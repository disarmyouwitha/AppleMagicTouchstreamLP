# Windows trackpad takeover investigation

Status: instrumentation implemented; exclusive takeover unverified. The controlled Bluetooth PTP-toggle capture on 2026-10-22 suppressed native movement/wheel events and restored successfully, but failed to preserve usable contacts. No persistent setting or device configuration change remains.

The follow-up [Apple driver Ghidra and REA report](WINDOWS_APPLE_DRIVER_GHIDRA_FINDINGS.md) contains the current binary entry points, HID descriptor map, feature-report analysis, and the next controlled test. It supersedes the initial binary-search hypotheses below where they differ.

Latest static pass: the apparent `0x00/0x00` usage was traced to an undersized `RID_DEVICE_INFO` interop declaration. Correct 32-byte queries and independent HID capabilities identify both input collections as **PTP `0x0D/0x05`**. The Apple `Col02` sibling supplies the captured reports and is itself PTP; disabling the open-source child is therefore not a demonstrated isolation mechanism. The installed open-source binaries expose no takeover command in the inspected dispatch paths. The latest Windows decompilation rejects direct PT_TOUCHPAD redirection and identifies an injection-device guard on the per-device setter. A read-only getter successfully captured all eight engine properties on both collections. A new internal MIT interception path skips PTP gesture starts and shell actions, but enable requires the session input thread and the inspected callback registration requires DWM identity; see the report's [ranked paths forward](WINDOWS_APPLE_DRIVER_GHIDRA_FINDINGS.md#paths-forward-assessed-after-this-research-pass). That inspected route is unavailable to an ordinary GlassToKey process. No new physical test is requested yet; next investigate whether any existing app-readable collection exposes complete contacts before PTP conversion.

## Windows PTP toggle finding

**Controlled run result:** [ptp-toggle-20261022-133717-030.log](../ptp-toggle-20261022-133717-030.log) contains 407 frames between the confirmed disabled status and `OS_RESTORE`. All have zero contact count and zero contact-slot bytes, while scan times continue changing. No non-injected mouse events occur in that interval; the tagged injected move changes the observed cursor position. The three positive frames labeled `osEnabled=False` arrive **after** `OS_RESTORE`, before the next status poll refreshes the cached flag. They are restoration frames, not evidence of usable contacts during suppression. The watchdog confirms enabled state at exit. Native suppression worked, but this stream cannot supply the engine with contacts during that interval. See the [detailed timing and payload assessment](WINDOWS_APPLE_DRIVER_GHIDRA_FINDINGS.md#controlled-bluetooth-result-2026-10-22-1337-local). USB, click suppression, shell gestures, and ordinary-mouse independence remain separately unverified.

Use `.\GlassToKey.Windows\WindowsDiagnostics\Run-PtpToggleProbe.ps1` from `windows_linux` for the controlled test. It shows progress, supplies the toggle argument, and preserves each capture in a new log. The user's first `ptp-os-toggle-controlled.log` was a complete 25-second observation run with `osToggle=False`; it did not exercise suppression.

`SPI_GETTOUCHPADPARAMETERS` works on this host and initially reported `touchpadEnabled=true`, `touchpadActive=true`, five supported contacts and no external mouse. The documented Ctrl+Win+F24 hotkey changed `touchpadEnabled` to false, then back to true after ten seconds. The helper starts a separate restore watchdog before toggling; the watchdog confirmed enabled state at exit. The test also logged one tagged `SendInput` move while disabled. No administrator access was needed.

Earlier, in two uncontrolled captures, the `0x05`/50-byte Raw Input stream continued while Windows PTP was disabled, but the contact count was zero for all 408 frames in one run and for 459 of 463 frames in the next. In the payload capture, 459 disabled-state frames also had all-zero contact-slot bytes; the four nonzero frames were near a state transition. Enabled-state frames had 695 positive contact counts out of 703. Those earlier runs lacked an instructed continuous touch, so they were inconclusive. The controlled run above now fails the contact-preservation criterion. Do not promote the global toggle to production. It also affects all Windows Precision Touchpads, including the built-in Dell pad on this host.

The current diagnostic waits for a live positive-contact frame between seconds 5 and 12 before issuing the toggle. For a controlled run, start `GlassToKey.Windows.exe --ptp-diagnostic <new-log-path> --ptp-os-toggle-probe`, place and keep a finger on the Bluetooth trackpad before second 5, then move it continuously through the ten-second disabled interval. Also try two-finger scrolling and a three/four-finger shell gesture during that interval. The program logs raw contact counts, low-level mouse messages, actual cursor coordinates, and PTP state, restores at ten seconds, and exits at 25 seconds. Escape restores early. If no live contact appears in the trigger window, it skips the toggle. Its independent watchdog checks restoration after 23 seconds. Repeat separately for USB when attached; do not change driver binding or PnP state to do so.

The exact installed open-source INF version `2025.3980.1.1000` matches the upstream [v2.0 INF](https://github.com/vitoplantamura/MagicTrackpad2ForWindows/blob/v2.0/build/AmtPtpDevice_AMD64.inf). In [v2.0 `Hid.c`](https://github.com/vitoplantamura/MagicTrackpad2ForWindows/blob/v2.0/AmtPtpHidFilter/Hid.c), input-mode and selective-reporting feature writes set `PtpInputOn`, `PtpReportTouch`, and `PtpReportButton`; a source-wide search finds no reads of those fields. The [control device](https://github.com/vitoplantamura/MagicTrackpad2ForWindows/blob/v2.0/AmtPtpHidFilter/ControlDevice.c) handles only settings reload and battery IOCTLs, also confirmed in the installed KMDF binary. This does not expose a takeover switch. The PnP tree shows a PTP child of the open-source filter on `Col01` and a separate Apple `Col02` PTP sibling. The latter's friendly name is auxiliary, but its actual usage is PTP. The former's isolation would not itself eliminate the latter's native interpretation. No devnode changes were made.

## First host run (2026-10-21)

The opt-in gate probe completed its full 25 seconds and logged automatic gate release. [Probe log](../ptp-takeover-probe.log) records 885 `0x05`/50-byte reports on usage `0x00/0x00` from tag `1:4390FD57`; 394 arrived while the gate was active. The hook saw 407 movement, 202 vertical wheel, and 4 horizontal wheel events overall. During the gate it saw 119 movement, 128 vertical wheel, and 4 horizontal wheel events. The gate returns nonzero for non-injected movement, while wheel events pass through. The one synthetic move returned `sent=1` and reached the hook with `LLMHF_INJECTED` and tag `0x47544B50`. All other logged mouse events had flags and extra info zero; this does not identify their source. The two enumerated device paths are collections of the same Bluetooth `PID_0324` instance, and only one delivered raw frames. This run does **not** establish two physical trackpads or USB behavior. The log does not measure actual cursor position or shell gesture actions, so those results remain unknown. It establishes only that the raw stream survives this mouse hook gate, not that it survives disabling PTP interpretation.

## Reversible hardware probe

Build `GlassToKey.Windows.csproj` and start `GlassToKey.Windows.exe --ptp-diagnostic <absolute-log-path>`. The diagnostic exits after 25 seconds. It starts no typing engine, does not save settings, and records every detected Magic Trackpad Raw Input report by device tag, usage, size and report ID. `RAW_COUNT` lines summarize counts. It records `WM_MOUSEMOVE`, `WM_MOUSEWHEEL`, and `WM_MOUSEHWHEEL` with `MSLLHOOKSTRUCT` coordinates, data, flags, Windows timestamp, extra info and a monotonic timestamp. These hook events have **no device identity**; correlation with raw reports is temporal only.

For the movement experiment, add `--ptp-movement-gate`. At 5 seconds it swallows only non-injected `WM_MOUSEMOVE` for at most 10 seconds, then releases automatically. At 8 seconds it injects one tagged 20-pixel `SendInput` move. Press **Escape** to release immediately and exit. The hook itself checks the deadline, so a stalled timer fails open. Process exit and exceptions dispose the hook. During the gate, manually test one-finger motion, two-finger scrolling, and three/four-finger shell gestures separately for each connected USB and Bluetooth trackpad. Record actual cursor and shell behavior alongside the log. An ordinary mouse will also lose physical movement during this temporary gate; this is why it cannot be the final design.

The diagnostic does not prove that native movement stops simply because a hook event was swallowed; compare the visible cursor before and during the gate. Likewise it does not prove that `0x05` raw reports survive a future PTP-specific suppression mechanism. The current gate does not suppress PTP interpretation, scrolling, or gestures.

## Current machine and package evidence

Read-only `pnputil` enumeration found a connected Bluetooth `PID_0324` Apple Precision Trackpad parent using `oem94.inf` (Apple, version `6.1.8000.6`) and its `Col01` child using `oem149.inf` (Bingxing Wang/Vito Plantamura, version `2025.3980.1.1000`). Therefore this is a **mixed driver stack**. The active open-source package contains `AmtPtpHidFilter.sys` (50,400 bytes) and `AmtPtpDeviceUsbUm.dll` (68,936 bytes). `oem38.inf` is a staged Apple USB package; enumeration did not establish that USB is connected. The untracked local `ApplePrecisionTrackpad_amd64.USB-C` package has `ApplePrecisionTrackpadUSB.sys` (37,784 bytes, SHA-256 `944447638112D32AF6FC2CDB4E47BFB75871600B7CDE97DADE3606C22B6AD4A1`) and `ApplePrecisionTrackpadBluetooth.sys` (41,896 bytes, SHA-256 `A589ABCB198326D84F1310FC8A5D9A9A5A2F4D219A55B15181FEEBA9E6893B92`), both file version `6.1.8000.6`. These binary hashes exactly match the staged DriverStore copies. Their INFs install them as per-device HID lower filters. The staged USB INF lists `PID_0265&MI_01` but not `PID_0324&MI_01`; the staged Bluetooth INF lists `PID_0265`, not `PID_0324`. The `PID_0324` parent is nevertheless bound to `oem94.inf`, apparently through a manual driver selection; this binding was not changed or tested. Both Apple binaries import WDF loader functions and contain PDB paths; a basic string scan found no obvious user-mode control interface. That is weak negative evidence, not a reverse-engineering conclusion.

`OFFICIAL_PTP_SPEC.md` identifies the 50-byte `0x05` report. Its prior `0x00/0x00` usage label came from failed metadata lookup and fallback, not a successful native query. Corrected standalone queries reconcile the live Apple `Col02` path with the embedded Touch Pad descriptor: actual usage is `0x0D/0x05`. Populated contacts did not persist during the controlled Bluetooth global-toggle interval. A production metadata fix must also preserve Apple's distinct byte packing; changing the structure alone would change decoder selection. Production behavior was left intact.
